## Design Decision: Token Approach

### Option A: `PasswordResetTokenGenerator` pattern

Use Django's `PasswordResetTokenGenerator` subclass — no database model needed.

| Factor | Assessment |
|--------|------------|
| Database model | None required |
| Migration | None required |
| State | Stateless — token is a signed string |
| Revocation | Invalidated automatically when user fields change |
| Tracking | No "used" flag — token is single-use by design |
| Complexity | Low — follows existing password reset pattern |
| Pattern match | Identical to password reset |

### Option B: Database-stored `VerificationToken` model (chosen)

| Factor | Assessment |
|--------|------------|
| Database model | `VerificationToken` with `user`, `token_hash`, `purpose`, `is_used`, `expires_at` |
| Migration | Required (already exists) |
| State | Stateful — token hash stored in DB |
| Revocation | Explicit — can mark `is_used=True` |
| Tracking | Full audit trail: `ip_address`, `user_agent`, `created_at` |
| Complexity | Medium — model with validation logic |
| Pattern match | Different from password reset, but more auditable |

### Decision: Option B

Option B was chosen because:
1. The `VerificationToken` model was already implemented for the password reset flow — reused, not duplicated
2. Full audit trail of token usage (IP, user-agent, timestamps)
3. Explicit token invalidation — prior unused tokens for same user+purpose are automatically marked used
4. Configurable expiry per token (`TOKEN_EXPIRY_HOURS` from settings, default 24h)
5. Shared model handles both `EMAIL_VERIFICATION` and `PASSWORD_RESET` purposes via `TokenPurpose` enum

### Code Flow

```

        ├── request.user (from JWT)
        ├── Already verified? → return silently

        │     ├── request.get_host() → protocol + domain
```

## API Endpoints

### Send Verification Email

**POST** `/api/v1/auth/send-verification/`

Auth: Required (`IsAuthenticated`)

**Request:**
```json
{}
```

**Response (200, always):**
```json
{
  "detail": "Verification email sent."
}
```

**Behavior:**
1. Get user from JWT (`request.user`)
2. If `email_verified` is already `True`: return 200 silently (no email sent)
3. Generate token: `VerificationToken.create_for_user(user, purpose=EMAIL_VERIFICATION, ip_address, user_agent)`
4. Extract domain: `request.get_host()` (no hardcoded fallback)
5. Build verification link: `{protocol}://{domain}/verify-email?token={token}&email={user.email}`
6. Render email templates (`email_verification/email_subject.txt`, `email_body.html`, `email_body.txt`)
7. Send email via `send_mail()` — wrapped in try/except
8. Log `verification_requested` to audit logger
9. Return 200 (always — prevent enumeration)
10. Throttle: 3/hour per user (`ResendVerificationThrottle`)

**Error responses:**

| Status | Condition |
|--------|-----------|
| 403 | No auth token (DRF default) |
| 405 | GET instead of POST |

### Verify Email

**POST** `/api/v1/auth/verify-email/`

Auth: Not required (token-based)

**Request:**
```json
{
  "token": "AbC123...",
  "email": "user@example.com"
}
```

**Response (200):**
```json
{
  "detail": "Email verified successfully."
}
```

**Behavior:**
1. Normalize email (strip + lowercase)
2. Look up user by email (active only)
3. If user not found: return 400 `"Invalid verification link."`
4. If `email_verified` is already `True`: return 200 `"Email is already verified."`
5. Validate token: `VerificationToken.validate_token(user, raw_token, EMAIL_VERIFICATION)`
6. If token invalid/expired: return 400 `"Invalid or expired verification link."`
7. Set `user.email_verified = True` + `user.save(update_fields=["email_verified"])`
8. Mark token as used: `token_instance.mark_used()`
9. Send welcome email via `_send_welcome_email()`
10. Log `verification_confirmed` to audit logger
11. Return 200
12. Throttle: 10/hour per IP (`EmailVerificationThrottle`)

**Error responses:**

| Status | Condition |
|--------|-----------|
| 400 | Invalid token, expired token, wrong email, missing fields |
| 405 | GET instead of POST |

## Token Lifecycle

### VerificationToken Model

**Token creation:**
```
VerificationToken.create_for_user(user, purpose, ip_address, user_agent)
  ├── Invalidate prior unused tokens for same user + purpose
  ├── Generate raw token: secrets.token_urlsafe(32) (~43 chars)
  ├── Hash token: SHA-256(raw_token) → 64-char hex digest
  ├── Store hash in DB (raw token never persisted)
  ├── Set expiry: now + TOKEN_EXPIRY_HOURS (default 24h)
  └── Return: (token_instance, raw_token)
```

**Token validation:**
```
VerificationToken.validate_token(user, raw_token, purpose)
  ├── Hash raw_token: SHA-256(raw_token)
  ├── Query DB: user + token_hash + purpose + is_used=False
  ├── Not found? → return None
  ├── is_valid()? → not is_used AND now < expires_at
  ├── Not valid? → return None
  └── Return: token_instance
```

**Token invalidated when:**
- `mark_used()` called → `is_used=True` → DB query won't match
- Expires → `now >= expires_at` → `is_valid()` returns False
- New token requested for same user+purpose → old token marked used via `create_for_user()`

**Single-use guarantee:**
After successful verification, `token_instance.mark_used()` sets `is_used=True`. Any subsequent validation attempt queries `is_used=False` and won't find the token.

## Audit Logging

All verification events are logged to `logs/audit.log` via Django's `"audit"` logger.

### Logged Events

| Event | Logger call | When |
|-------|-------------|------|
| `verification_requested` | `audit_logger.info(...)` | User requests a verification email (SendVerificationView) |
| `verification_confirmed` | `audit_logger.info(...)` | Email successfully verified (VerifyEmailView) |
| `verification_already_verified` | `audit_logger.info(...)` | Verify endpoint called but email already verified |
| `verification_failed` | `audit_logger.info(...)` | Invalid/expired token submitted to verify endpoint |

### Log Format

```
verification_requested user_id=1 email=user@example.com already_verified=False ip=127.0.0.1
verification_confirmed user_id=1 email=user@example.com ip=127.0.0.1
verification_already_verified user_id=1 email=user@example.com ip=127.0.0.1
verification_failed email=user@example.com reason=invalid_token ip=127.0.0.1
```

### Logger Configuration (`config/settings/logging.py`)

```python
"audit": {
    "handlers": ["audit"],
    "level": "INFO",
    "propagate": False,
},
```

Handler writes to `LOG_DIR / "audit.log"` with verbose formatter (timestamp, level, module, etc).

## Configuration

### Settings (`config/settings/security.py`)

Token expiry is controlled by:

```python
# In authentication/models.py
TOKEN_EXPIRY_HOURS = getattr(settings, "VERIFICATION_TOKEN_EXPIRY_HOURS", 24)
```

Default: 24 hours. Override via `VERIFICATION_TOKEN_EXPIRY_HOURS` in environment or settings.

### Throttles (`authentication/throttles.py`)

```python
class EmailVerificationThrottle(AnonRateThrottle):
    rate = "10/hour"          # Verify endpoint (public)
    scope = "email_verification"

class ResendVerificationThrottle(UserRateThrottle):
    rate = "3/hour"           # Send endpoint (authenticated)
    scope = "resend_verification"
```

### URLs (`authentication/urls.py`)

```python
path("send-verification/", SendVerificationView.as_view(), name="send_verification"),
path("verify-email/", VerifyEmailView.as_view(), name="verify_email"),
```

### Domain Extraction

All email serializers extract the domain from the incoming request:

```python
request = self.context.get("request")
protocol = request.scheme if request else "https"
domain = request.get_host() if request else "localhost"
```

No hardcoded domain defaults. In production, `request.get_host()` returns the actual `Host` header value (e.g., `elahopos.com`). In tests, DRF's test client sends `testserver`.

## Security Assessment

### The Good

| Measure | Implementation |
|---------|---------------|
| Enumeration prevention | Send endpoint always returns 200 |
| Timing-safe token validation | DB lookup is constant-time; `is_valid()` is simple boolean check |
| Single-use tokens | `mark_used()` sets `is_used=True`; DB query filters `is_used=False` |
| Time-limited tokens | Configurable expiry (default 24h) via `TOKEN_EXPIRY_HOURS` |
| User-bound tokens | Token lookup includes `user` FK — can't cross accounts |
| SHA-256 hashed tokens | Raw token never stored; only 64-char hex digest in DB |
| Rate limiting | 3/hour send (authenticated), 10/hour verify (public) |
| Already-verified check | No email sent if already verified; verify returns 200 "already verified" |
| Audit trail | `ip_address`, `user_agent`, `created_at` on every token; audit logger for all events |
| Automatic invalidation | New token request marks all prior unused tokens as used |
| Historical records | `VerificationToken.history` tracks all changes via django-simple-history |
| `send_mail` error handling | All `send_mail` calls wrapped in try/except — SMTP failures logged, don't break API |
| Dynamic domain extraction | `request.get_host()` used instead of hardcoded defaults |
| Welcome email | Sent only on first verification, not on resend |

### Remaining Concerns

| # | Severity | Finding | Mitigation |
|---|----------|---------|------------|
| 1 | MED | **Login does not block unverified users** | By design — configurable per business later |
| 2 | LOW | **Token in URL query string** — can leak via Referer headers | Standard practice; HTTPS + `SECURE_REFERRER_POLICY=same-origin` mitigates |
| 3 | LOW | **No explicit token cleanup** — expired tokens accumulate in DB | Add periodic cleanup task or rely on `is_used` index |
