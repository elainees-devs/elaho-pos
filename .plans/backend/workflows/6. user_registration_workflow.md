## Current State

User creation is **partially implemented**. The `UserViewSet` provides full CRUD. Permission checks use `HasPermission(PermissionCode.USER_CREATE)` — Admin and Manager roles have this permission, Staff does not.

### What exists today

| Component | Status | Notes |
|-----------|--------|-------|
| User CRUD endpoint | **Implemented** | `POST /api/v1/users/` — requires `user.create` permission |
| User list/retrieve | **Implemented** | `GET /api/v1/users/` — requires `user.view` permission |
| User update | **Implemented** | `PATCH /api/v1/users/{id}/` — requires `user.update` permission |
| User delete | **Implemented** | `DELETE /api/v1/users/{id}/` — requires `user.delete` permission |
| User.business FK | **Implemented** | Nullable FK to Business |
| Business-scoped queries | **Implemented** | `get_queryset()` filters by `request.user.business` |
| Auto-set business FK | **Implemented** | `UserSerializer.create()` sets `business` from `request.user.business` |
| Owner linking on create | Not implemented | Business.owner stays NULL |

## Who Can Create Whom

### Permission Matrix

| Creator Role | Can Create | Cannot Create |
|--------------|-----------|---------------|
| **Superadmin** | Any user for any business (owner, manager, staff) | — |
| **Admin** (level 100) | Manager, Staff — within their business | Owner (superadmin-only) |
| **Manager** (level 50) | Staff — within their business | Owner, Manager |
| **Staff** (level 10) | No one | All |

### Role Assignment Rules

| Role | Assigned By | Notes |
|------|-------------|-------|
| Owner | Superadmin only | First user of a business, linked via `Business.owner` |
| Manager | Superadmin or Admin | Operations manager with full user CRUD |
| Staff | Superadmin, Admin, or Manager | Frontline staff with minimal permissions |

### Business Scoping

| Scenario | Behavior |
|----------|----------|
| Superadmin creates user | Can assign to any business (or no business) |
| Admin creates user | User is assigned to admin's business |
| Manager creates user | User is assigned to manager's business |
| Cross-business creation | Not permitted (pending enforcement) |

## API Endpoints

### Create User

**POST** `/api/v1/users/`

Auth: Required + `user.create` permission

**Request:**
```json
{
  "email": "cashier@example.com",
  "password": "securepassword123",
  "first_name": "Jane",
  "last_name": "Mwangi",
  "phone": "0722222222",
  "role": 3
}
```

**Response (201):**
```json
{
  "id": 456,
  "first_name": "Jane",
  "last_name": "Mwangi",
  "email": "cashier@example.com",
  "phone": "0722222222",
  "role": 3,
  "is_active": true,
  "created_at": "2026-07-15T10:30:00Z"
}
```

**Processing:**
1. Check `user.create` permission on creator's role
2. Normalize email (strip + lowercase)
3. Title-case first_name and last_name
4. Hash password via `set_password()`
5. Create user record
6. Return user (password excluded)

**Error responses:**

| Status | Condition |
|--------|-----------|
| 400 | Missing fields, duplicate email, weak password |
| 401 | No auth token |
| 403 | Missing `user.create` permission |
| 405 | GET instead of POST |

### Retrieve User

**GET** `/api/v1/users/{id}/`

Auth: Required + `user.view` permission

**PATCH** `/api/v1/users/{id}/`

Auth: Required + `user.update` permission

**Response (200):** Updated user object.

### Delete User

Auth: Required + `user.delete` permission

## Security Assessment

### The Good

| Measure | Implementation |
|---------|---------------|
| Permission-based access | `HasPermission(PermissionCode.USER_CREATE)` on viewset |
| Role hierarchy | Admin (100) > Manager (50) > Staff (10) |
| Password hashing | `set_password()` via PBKDF2 |
| Password excluded from response | `write_only=True` on password field |
| Email normalization | `strip().lower()` in model `clean()` |
| Name normalization | `strip().title()` in model `clean()` |

### Remaining Concerns

| # | Severity | Finding | Mitigation |
|---|----------|---------|------------|
| 1 | MED | **Business.owner not linked** — owner stays NULL after user creation | Add owner linking logic |
| 2 | MED | **No email uniqueness per business** — same email in multiple businesses | Add unique constraint or validation |
| 3 | LOW | **No soft-delete enforcement** — deleted users still accessible by ID | Filter `is_deleted=False` in queryset |

## Known Issues

### Recommended Next Steps

1. **Business-scoped queryset** — `UserViewSet.get_queryset()` filters by `request.user.business`
2. **Auto-set business FK** — `UserSerializer.create()` sets `business` from `request.user.business`
3. **Owner linking** — when creating a user with Manager role for a business with no owner, set `Business.owner`
4. **Cross-business access prevention** — Manager/Admin can only see/manage users in their own business
5. **Email uniqueness per business** — validate email doesn't already exist in the same business
6. **Soft-delete in queryset** — filter `is_deleted=False` in `get_queryset()`
